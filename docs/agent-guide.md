# JoomEngine Playground: guide for people and agents

JoomEngine Playground is a browser-based workspace for creating, testing and improving Joomla extensions with **Joomla Component Builder (JCB)**. It runs Joomla and PHP in WebAssembly and a real MariaDB engine in browser workers. People can use JCB's administrator interface, inspect the site's files in JoomEngine Code, compile an extension, and test its installed behavior. An agent with compatible browser controls may be able to perform the same sequence, but its access and each end-to-end workflow must be verified. The Playground is also useful for testing Joomla itself and other trusted extensions.

This guide is an operational starting point, not an assurance that every extension or workflow is compatible. Follow the links for the current version-specific contracts and verify the environment and each result. An agent needs a browser tool that can interact with the Joomla iframe and handle downloads/uploads; documentation alone does not grant browser access, repository credentials or publication authority.

## Start here

1. Open [Playground with setup shown](https://playground.joomengine.org/?start=0). In **Deployment**, choose a suitable Joomla release, PHP runtime, and the **JCB** deployment, then inspect any other settings. Available choices come from the deployed catalog; the [source catalog](https://github.com/joomengine/playground/blob/main/versions.json) records the repository's pinned builds. Do not assume that an arbitrary release, a newer patch, or a version absent from the selector is available.
2. Decide whether the work needs a temporary site or a saved site. For independent clean testing, choose **New site** or use `fresh=1`; the latter also bypasses prepared snapshots and builds the chosen recipe. Launch, wait for provisioning and the actual Joomla/JCB page, and note the effective versions. A normal visit may instead reopen the last used saved site.
3. Record the Joomla, PHP and installed JCB versions, deployment, browser, candidate repository/branch/commit and relevant package checksums. An existing saved site may contain an older JCB than the current default. Prepared installations are pinned and are not automatic latest-version downloads.
4. To build or test JCB models, follow the [JoomEngine JCB skill router](https://github.com/joomengine/skills/blob/main/SKILL.md), its [agent operating contract](https://github.com/joomengine/skills/blob/main/AGENTS.md), and the relevant model workflow linked below. Then test the actual compiled and installed consumer, not just the import.
5. Save useful work in the running site and **Download** a complete backup when needed. Report the separate results of acquisition, compilation, installation and runtime testing, including anything blocked or not run.

## Choose and configure a site

Rocket's Deployment editor offers the supported Joomla and PHP combinations, deployment presets, site name, login behavior, packages, language, menus, template and advanced settings. Use the **Site** and **Admin** controls to navigate the already-running preview. Admin follows Joomla's authentication flow; **Credentials** displays the generated administrator details when required. A fresh site receives new credentials.

- **JCB** prepares an authoring site; **Joomla only** is useful for testing a compiled package on a clean installation. Other presets can change as recipes are added or removed. Review the live selector and [deployment guide](https://github.com/joomengine/playground/blob/main/deploys/README.md).
- Changes are staged and validated at launch. Changing the Joomla release or deployment selects a separate profile; it does **not** upgrade the Joomla installation in an existing site. Supported PHP changes preserve its files and database, but still record the effective PHP version and settings.
- `?start=0` suppresses the startup countdown so configuration can be reviewed. Other supported URL parameters include `deploy`, `joomla`, `php`, `path`, `persist`, `fresh`, `language`, `login`, `extensions`, `commands`, and `config`. Values are validated against available catalog entries. The [URL reference](https://github.com/joomengine/playground#embedding-and-url-configuration) explains syntax and precedence.
- A Joomla path and its query string must be encoded as one `path` value. For example, `/administrator/index.php?option=com_componentbuilder&view=compiler` becomes `path=%2Fadministrator%2Findex.php%3Foption%3Dcom_componentbuilder%26view%3Dcompiler`. The path chooses a screen, not a repository branch or a tested candidate.
- **Use** starts an independent deployment using the edited configuration. **Apply to this site** checkpoints and applies supported changes to the running site; review packages and commands first. Removing a package from configuration does not uninstall it. Failed application offers recovery from its checkpoint as a separate site.
- Startup commands are arrays of Joomla CLI arguments, for example `[["cache:clean"]]`; they are not host shell commands. They run after package installation, and a completed site's original commands are not replayed on reopen.

For reproducibility, retain an exported deployment JSON or Share link plus actual versions and checksums. Share contains public configuration, not saved Joomla files, database content, site credentials or evidence that a test ran. The generated link has size limits; larger public configurations can be exported/imported as JSON or hosted where the browser can fetch them. Avoid putting secrets in URLs, command arguments or shared configuration. See the [deployment document schema and guide](https://github.com/joomengine/playground/blob/main/deploys/README.md#compose-a-deployment-without-a-repository-change).

## Install another Joomla extension

In **Deployment → Extension packages**, add a trusted ZIP URL and optionally its SHA-256; add further rows for other packages. Use the deployment as a new site or apply it to the current site. The separate advanced JSON editor accepts objects with `url` and optional `sha256`. Alternatively use Joomla's normal supported extension installer in the running administrator interface when your browser can supply the package. Wait for the result and inspect the installed extension; choosing a ZIP is not proof of successful installation.

Remote ZIPs require HTTPS (localhost HTTP is allowed for development), CORS access from the browser and a size within the current 128 MiB package limit. A supplied checksum is verified. Browser memory, Joomla/PHP upload settings and package compatibility may impose additional limits. The deployment installer has its own time budget; a timeout or partial installation needs diagnosis or recovery rather than an assumed success. Installed extension code can access Playground-origin site data: use trusted packages and test data, and do not treat separate site keys as security isolation.

## Understand JCB's sources and results

JCB uses authoring records and linked models to generate Joomla extensions. A component blueprint may include views, fields, permissions, code, assets and references to reusable dependencies. The precise structure and serialization depend on the model and JCB revision. Do not treat one JSON file, a compiled extension ZIP or installed PHP files as the complete editable blueprint. The [JCB architecture publication](https://architecture.joomlacomponentbuilder.com/) and [model router](https://github.com/joomengine/skills/blob/main/packages/models/README.md) provide the conceptual and field-specific detail.

Use the complete [JoomEngine Skills distribution](https://github.com/joomengine/skills) and select the task-specific entry point:

| Work | Read first | Important distinction |
| --- | --- | --- |
| Component, module or plugin blueprint | [Packages skill](https://github.com/joomengine/skills/blob/main/packages/SKILL.md) and [model contracts](https://github.com/joomengine/skills/blob/main/packages/model-contracts.json) | A package is a graph of records, dependencies and assets. Identity and encoding differ by model. |
| Reusable PHP class/interface/trait | [Super Powers skill](https://github.com/joomengine/skills/blob/main/super-powers/SKILL.md) | `settings.json` and `code.power` are import inputs; preserve existing identities and keep derived files/index consistent. |
| Field Type catalog | [Field Types skill](https://github.com/joomengine/skills/blob/main/field-types/SKILL.md) | A Field Type is reusable metadata; a concrete Field is a separate JCB authoring record. |
| Reusable view source | [Snippets skill](https://github.com/joomengine/skills/blob/main/snippets/SKILL.md) | A snippet is copied into a consumer; updating its catalog does not automatically rewrite previously copied content. |
| Import, compile and exercise any model | [Playground integration workflow](https://github.com/joomengine/skills/blob/main/testing/playground/README.md) | Record acquisition, persisted records, compilation, installation and runtime checks separately. |
| Create a blueprint in JCB and export its source | [GUI authoring and export](https://github.com/joomengine/skills/blob/main/packages/workflows/author-in-playground.md) | JCB source Push is different from downloading a compiled component ZIP. |

These are the AI-oriented operational docs for JCB; load their linked references and source evidence as required. Skills describe workflows and contracts; they do not install themselves or provide tools or credentials. Consult the [loading guide](https://github.com/joomengine/skills/blob/main/standards/skill-loading.md) when supplying a complete portable skill distribution to an agent. Check current documentation and target source revisions, because fields and supported versions can change.

For machine-readable architecture documentation, start with [llms.txt](https://architecture.joomlacomponentbuilder.com/llms.txt), the [article index](https://architecture.joomlacomponentbuilder.com/articles.json), or the [complete Markdown download](https://architecture.joomlacomponentbuilder.com/downloads/jcb-architecture-complete.md). The [architecture skill references](https://github.com/joomengine/skills/blob/main/architecture/README.md) explain how to navigate these resources. For human-oriented tutorials, see the [JCB documentation index](https://github.com/joomengine/jcb-documentation/blob/master/english/index.md).

## Build or test a JCB model

1. Identify the task, authorized source repository, target Joomla/JCB/PHP versions, model and dependencies. Read the matching skill, contract and workflow above. Perform its source validation and identity/collision checks. Record the exact candidate commit; a branch name alone can move.
2. Start a suitable independent JCB site. Open JCB's **Repositories** area, inspect existing entries, and configure or enable only the candidate and required dependencies: content target, provider/host, organization, repository, **read branch**, enabled state and precedence. The Playground deployment URL does not select a JCB repository read branch. Check the effective selected source and any fallback, especially for intentional overrides. Never place tokens in a public URL, report or screenshot.
3. In the relevant JCB list, use the supported **Init**, **Pull** or **Reset** flow for the installed version. Init may preserve an already-local item; a selection page or success notification alone does not prove that candidate data was loaded. Reset can overwrite local changes. Save/reopen and inspect the relevant identity, content and dependencies. JCB's entity Reset is distinct from Playground's site Reset.
4. Build a real consumer: reference the Power from a caller; attach a concrete Field based on the Field Type to a view; copy a Snippet into an attached view; or connect the component/module/plugin graph and dependencies. Save and reopen the records to check persistence. Use the specific model's integration workflow for exact acceptance cases.
5. Open JCB's compiler, select the actual component and target, compile, and inspect messages. Use **Download Component** to retain the resulting ZIP, inspect its generated files and record a hash when possible. The generated extension ZIP is not the same thing as a portable JCB source repository or a full site backup.
6. Install the package in a compatible disposable Joomla site using an available supported package upload or URL flow. Exercise the relevant admin/frontend behavior and boundaries, verify saved data, and inspect generated/installed files where relevant. A successful import, compile or ZIP alone does not establish correct installed behavior.
7. If Code reveals a defect, use edits there as diagnostics; carry lasting changes back to the authoritative repository, JCB authoring records or compiler source as appropriate, then reimport/refresh, recompile, reinstall and retest. If a stage is unavailable, state exactly what was blocked and why.

A user can also author the component and related records in JCB's GUI and compile them there. For reusable blueprint source, follow the linked authoring workflow's **Push** and read-back procedure. Check *all* eligible writable package destinations before Push: an apparently selected root does not guarantee a single destination. Write only to authorized repositories/branches and verify exported records, indexes and assets in a separate test. If publication or credentials are unavailable, report that source export as blocked rather than pretending a downloaded extension is a blueprint.

## Inspect files and debug

Open **JoomEngine Code** from the Playground header. Its workspace is the active site's Joomla document root, `/persist/www`. Browse, search, open and edit available site files; use editor **Save** or **Save All** before checking behavior, and **Refresh site** when a preview reload is required. Code's workspace is not automatically a checkout of the model repository, and editing installed files does not update JCB records held in the database. Playground **Save** is a separate operation that persists site files and database.

For a PHP problem, set a breakpoint in executable source and use **Debug and refresh** for the current GET, or **Arm PHP request** with the exact URL, query and method before the relevant form/navigation. Inspect the stack and variables and continue/step. Debugger expression evaluation can have side effects. While a request is paused, other requests and source saves can queue; continue or stop before waiting on them. Stopping a request does not roll back database writes already completed. See the [Code user guide](https://github.com/joomengine/playground/blob/main/docs/joomengine-code-user-guide.md) and [debugger notes](https://github.com/joomengine/playground/blob/main/docs/joomengine-code-debugger.md).

The optional in-product AI Assistant can propose file changes using bounded context for review. Local editing and debugging do not require an AI key. A configured provider must support the browser connection, including its CORS restrictions; provider presets and protocol fixtures alone do not establish live account compatibility. Review changes and sensitive context before sending or accepting. Its capabilities are separate from those of an external agent. See [AI validation](https://github.com/joomengine/playground/blob/main/docs/roadmap/ai-validation.md).

## Save, download and move work

| Action | What it does |
| --- | --- |
| Editor Save | Writes a file to the active virtual site. Unsaved editor buffers are not portable exports. |
| Playground Save | Flushes site files and database to browser storage. Wait for success; browser storage can be cleared or evicted and is not a backup. |
| Share / deployment JSON | Recreates public configuration for an independent installation; it does not carry the edited site files or database. |
| Download complete site | Produces a site archive with `site/`, `database.sql`, `database.ndjson`, `export.json`, and `DEPLOYMENT.md` for supported exports. |
| Files-only / SQL-only Download | Exports only that part; neither alone is a complete movable site. |
| JCB Download Component | Downloads the compiled Joomla extension; it is distinct from the site archive and editable blueprint source. |

For conventional Joomla hosting, open the complete archive's **DEPLOYMENT.md** and follow its destination-specific instructions: provision a compatible PHP/MariaDB environment, upload the Joomla files, import SQL into the target database, configure the destination database and paths as directed, and verify permissions and login. The export contains portable placeholder database settings; do not assume it runs unchanged. The existing Joomla administrator account's database record is exported, but browser sessions and Playground's private credential metadata are not. Arrange usable credentials securely before the move, and verify that the restored site and installed extensions work on that host.

Prepared-site imports use `database.ndjson` internally, and repository builds independently restore prepared snapshots. Do not confuse the UI's **Import configuration** with a documented general-purpose full-site restore button: it imports deployment settings, not the modified site's files/database. Consult the current Playground documentation and controls for any subsequently added private site-import workflow before promising a browser-to-browser restore. Keep archives private: site data, account password hashes and configuration can be sensitive. Not every MariaDB feature is exportable; export reports unsupported cases rather than silently completing. Follow the [export and lifecycle reference](https://github.com/joomengine/playground#using-rocket).

Closing a temporary site discards its state after confirmation. **Restart** preserves current site data. **Reset** deletes the selected site's files and database; preserve needed evidence first. **Recover saved site** can offer backup/recovery without booting Joomla, but a files-only recovery from a failed database contains no SQL and may include private settings. Only one tab can own a particular saved site at once.

## Platform boundaries and troubleshooting

- Playground uses a WebAssembly PHP environment and browser-managed MariaDB/PDO. Remote database connections, `mysqli`, arbitrary host processes, sockets and a production mail server are not supplied. Native server behavior, PHP integer size, extension dependencies and available browser memory can differ. Run relevant native-environment tests separately.
- PHP network requests use browser Fetch and require the destination's CORS permission. Browser security, HTTPS/mixed-content and network access apply. The project supplies no public CORS proxy. Diagnose network, authentication and rate limits separately from a model-format failure.
- A PHP request cannot complete a recursive HTTP request to the same busy Playground worker. The optional JCB + MCP deployment is useful for its supported authentication/discovery path, but content-editing actions requiring this recursive execution are not established as supported. A static public URL does not expose a browser-local site as a remote MCP server.
- Browser isolation requires supported browser features, secure origin/localhost and appropriate cross-origin isolation. If startup or installation fails, retain the visible activity and error, versions, settings and exact step; do not replay uncertain write operations without inspecting the state.
- Avoid treating site keys as private access controls. Use trusted extensions and appropriate test data. Keep the owning tab open while the site is in use; the raw preview depends on that runtime.

## Report a result another person can reproduce

Include the task and expected behavior; Playground build/revision if available; Joomla, PHP, installed JCB, deployment, browser and source repository/branch/commit; dependency sources and effective precedence; exact setup and actions; observed results; errors; generated package hash and relevant files; and a clear status for each of source validation, acquisition, record inspection, compilation, installation and runtime testing. Include separate native-server testing where required. Preserve a sanitized reproduction and relevant artifacts without credentials, personal data or private site archives.

Use the skills repository's [verification workflow](https://github.com/joomengine/skills/blob/main/testing/playground/README.md) and [issue-reporting guidance](https://github.com/joomengine/skills/blob/main/testing/reporting-issues.md). Historical validation is useful background, but it is not proof that the current candidate passed. Do not claim a stage passed unless it was actually performed.
