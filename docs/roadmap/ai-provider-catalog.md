# AI API provider implementation appendix

Research date: 30 October 2026. This is an implementation specification supported by official documentation, not a claim that authenticated browser connections have been tested. Recheck the linked documentation during implementation; model catalogs and regional endpoints change.

## Required user experience

- Name this settings area **AI API**. Order the provider selector **OpenAI**, **Anthropic / Claude**, **Google / Gemini**, then the other named presets, and **Other / Local AI API** last.
- Populate standard API configuration internally. For normal presets, ask for the API key and model; only reveal region, workspace, resource, or deployment fields when the provider actually requires them. A provider with a resource-specific endpoint cannot be configured from its brand name alone.
- Keep the broad preset catalog below in one extensible registry. Group model vendors, hosted inference services, and local/custom connections visually so that OpenRouter is clearly a gateway, not an unexplained model or a required account.
- **Other / Local AI API** must accept a user-specified base URL, supported API format, optional API key, and model. Allow more than one custom connection with a human-readable name. Offer examples for Ollama and LM Studio. Selecting a custom URL must never silently send it an existing named provider's API key.
- Use the label **AI API base URL** and the help text: “The address of the AI API server that will receive your requests. Enter its API base URL, not the address of its chat website.” Examples: `http://localhost:11434/v1` (Ollama), `http://localhost:1234/v1` (LM Studio), `https://ai.example.com/v1` (a hosted compatible API).
- The default custom API format should be **OpenAI-compatible Chat Completions**. Additional supported choices can include OpenAI Responses, Anthropic Messages, and Gemini. A URL alone does not establish wire-protocol compatibility; implement and test each offered adapter. Explain the choice in ordinary language and keep advanced settings collapsed.
- **Load models** retrieves a catalog; **Connect** can validate it without generating a billable completion. Do not assume every service has a model-list API, that a list is unauthenticated, or that every returned model supports chat and tools. Avoid using a generated response as a hidden connection test.
- Preserve the user's valid model choice. For a first choice, put currently available recommended coding/chat models first and preselect an appropriate one. Use provider capability metadata plus a small maintained preference policy; neither alphabetical order nor creation date is a sufficient recommendation policy. Exclude embeddings/audio-only/image-only and retired models. Distinguish a failed catalog request from an empty catalog. Provide a manual model identifier when discovery is unavailable, including for custom servers.
- API keys stay masked and usable for the open app session across closing/reopening settings, editor toggling, and detaching/redocking. Keep credentials in the existing isolated AI boundary; do not expose them to Joomla, saved-site exports, logs, shared URLs, or ordinary page storage. Add an explicit forget/disconnect action. Accounts and AI settings use the same connection state, rather than separate copies of the key.
- Remove development badges such as “Unverified” and “Verification required.” Keep useful operational feedback: key missing, connection failed, server unreachable, model unavailable, retry/load models. Do not make the UI present an untested adapter as connected.

## Engineering boundaries and acceptance criteria

1. **One registry, multiple adapters.** Registry entries carry display order, API kind, base/template, regional fields, authentication scheme, catalog method/parser, pagination, capabilities, and default-model preference policy. Keep provider labels separate from model names. The UI should not expose all these engineering fields for presets.
2. **Live discovery without a universal promise.** Load models after credentials/settings are supplied; cancel stale requests when provider changes. Cache per connection for the session and offer refresh. Catalog failure preserves a prior valid choice. Where official discovery is unavailable, show a maintained fallback and editable model field, with a useful operational message. Do not label all models “free”; catalog access and generation billing are different matters.
3. **Test from the actual browser boundary.** The existing isolated AI iframe may send `Origin: null`. Verify preflight, authentication headers, streaming, cancellation, tools, provider errors, and model listing from that exact context, including the detached editor. Documentation for a server SDK is not evidence of browser CORS support. Anthropic's TypeScript SDK explicitly makes browser support opt-in: [SDK](https://github.com/anthropics/anthropic-sdk-typescript).
4. **Make local servers usable without false assurances.** Test local HTTP loopback, user-configured HTTPS servers, browser local-network permission, and CORS behavior. Ollama has an `OLLAMA_ORIGINS` configuration: [FAQ](https://docs.ollama.com/faq). Show targeted setup help after an actual connection failure. Do not automatically scan local ports, disable browser protections, weaken the credential sandbox, or route requests through an undisclosed proxy. “Other” supports configured protocols, not arbitrary AI web pages.
5. **Scope is enforced end to end.** The selected current file/files/folder/project scope controls initial context and subsequent AI file reads/searches/tools. Keys or unrelated sensitive files must not leak when changing providers. Preserve existing diff review and accept/reject/undo behavior.
6. **Record tests separately from shipped UI.** Maintain adapter tests and a developer-only compatibility matrix with provider, browser, catalog, streaming, tool round-trip, cancel, and error results. For credential-dependent providers, clearly record tests not run. Do not ship the internal matrix's “unverified” badges in the user interface.

The catalog is intentionally broader than the original four providers. Implement all entries as real configured integrations, including the provider-specific routes above; merely adding names to a dropdown is not completion. If a provider is unavailable to the test account or needs a transport the browser application cannot supply, record that precise blocker in the handoff instead of silently advertising working support.
