## Companion catalog implementation fields

The appendix's engineering fields are represented by the [registry](../../src/code/ai-provider-registry.mjs), its selected [adapters](../../src/code/ai-provider.mjs), and [connection identity/settings](../../src/code/ai-connection-settings.mjs). They are not exposed as configuration burdens for normal presets.

| Required field or behavior | Implementation |
| --- | --- |
| Display order, groups, API kind | Ordered `AI_PROVIDERS`; `group` and `protocol` select UI grouping and wire adapter. |
| Base/template and regional/account fields | `baseURL` and `fields`; Qwen region/workspace, Fireworks account, Azure resource and Bedrock region/route derive their endpoints. |
| Authentication | `auth`, protocol headers and isolated credential fields; Bedrock inference API keys remain separate from optional AWS SigV4 catalog credentials. |
| Catalog method/parser and pagination | `catalog` selects bounded provider-specific GET discovery/parsing, including native Bedrock foundation models/inference profiles. Static/manual routes do not invent a model-list endpoint. |
| Capabilities and default policy | Catalog metadata filtering plus `preferences`; preserve a valid selected ID and retain manual deployment/model entry where capability or account data is insufficient. |
| Multiple local/custom connections | Human-readable session profiles, URL/format selection, templates and exact-profile forgetting in the panel/broker. Credentials are cleared when switching to a different endpoint identity. |
| Session cache and refresh | The isolated broker caches catalogs by connection and credential revision; explicit refresh and model entry remain available. |
| Errors and evidence | Adapters reject unsafe redirects, bound responses and redact credentials; protocol fixtures and account/browser limitations are recorded separately in [AI validation](ai-validation.md). |

## Validation boundary

Implementation publication is a separate milestone from acceptance verification. The complete implementation at `01e114d` passes 280 unit tests, JavaScript source checks and the pinned production build with three PHP runtimes and two Joomla distributions. The complete final-revision Chromium/Firefox suites and screenshot review must still be reconciled with the [PR checklist](https://github.com/joomengine/playground/pull/8#issuecomment-6526041362). Subsequent validation passed both complete runtime suites and both Rocket/chrome suites at `439bf9c`, alongside native editor/AI interaction checks. Validation exposed a real saved-name draft loss during catalog refresh, now fixed, plus tour-navigation and early debugger-stop timing assumptions now synchronized with application completion. Earlier passing stages do not make the full final-revision suite successful. The existing [visual evidence](evidence/README.md) identifies actual-shell images versus UI fixtures and their limits.

No authenticated cloud-provider smoke test or deployed-HTTPS browser test against a configured Ollama/LM Studio server is claimed. Protocol fixtures do not establish account access, browser CORS/local-network permissions, quota, model availability or Bedrock IAM permissions. Those remaining checks are detailed in [AI validation](ai-validation.md#remaining-real-service-checks).
